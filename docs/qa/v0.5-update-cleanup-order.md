# Update staging cleanup before relaunch

The combined gate at `6c5782e` passed the other Go packages but exposed a
staging-cleanup race in TestCheckDownloadVerifyAndInstall. `install` deferred
RemoveAll until after its Relaunch callback. A real relaunch may terminate the
process without returning, so cleanup must happen before that handoff.

The regression holds the Relaunch callback on a channel until its staging
assertions complete. On unchanged production code, the negative control failed
deterministically with staging left behind (`v05-update-cleanup-order-negative-control`,
exit 1). This is retained evidence, not a timing retry or relaxed assertion.

The fix explicitly removes only the newly owned staging directory after verified
swap, before publishing restarting or invoking Relaunch. The existing defer
remains an idempotent failure-path fallback. If explicit cleanup fails, the
sanitized error says the update is already installed and asks the person to quit
and reopen. It does not claim rollback or safe retry; the new bundle and original
backup/Trash state are not undone. Cleanup-failure fault injection remains separate
coverage; this regression exercises successful cleanup ordering.

Actual Go 1.26.10 macOS gates passed: 20 normal and ten race repetitions of the
held-callback regression, complete update normal/race tests, vet, and Windows/Linux
update test compilation (`v05-update-cleanup-order-correction-gate`, exit 0).
Independent bounded review approved the small code/test change with no required
findings. Tests replace only temporary ad-hoc-signed fake apps; no real relaunch,
application, vault or personal data is accessed.

Native CI and the repeated combined integration gate remain pending. This does
not add a new-platform installer, retained-parent restart identity, universal
power-loss safety or a transactional update protocol.
