# Desktop notification boundary (bounded v0.5 slice)

The desktop notifier uses `runtime.GOOS` and the same
`host.DesktopHumanConfirmationPolicy(FRONTEND_DEVSERVER_URL)` selection as setup.
Inline approval and yes/no buttons retain only legacy Darwin compatibility:
`darwin && !server && !mcp`, with no nonempty dev-server override. Windows,
Linux, unknown platforms, and denied modes do not register actionable categories
or send notifications with actions. Where a native service already exists, plain
notifications and callbacks that only show/focus the window remain available.
Native service creation is still bundle-dependent; this is not new platform
startup support or a notification/activation readiness claim.

Callback dispatch rechecks the selected capability, independently of category
registration. Before invoking a store, it requires the known action/category,
nonblank string request/agent or confirmation-field data, and the matching
notification identifier. Unknown, malformed, denied, SDK-error, and stale/store-error
callbacks open the UI instead. Host, Origin, window headers, and payload trust
flags grant no authority. The stores retain their existing pending-state checks.
This does not authenticate all API requests, attest native activation, or prove a
physical human gesture; central API authorization remains outside this slice.

When native delivery is unavailable or fails, only Darwin may invoke the absolute
`/usr/bin/osascript`, directly with `-e` and the existing escaped/truncated script.
The fallback has no buttons or UI-activation guarantee. The existing watch goroutine
waits synchronously: no goroutine is spawned per notification. `CommandContext`
has a three-second deadline; `Run` waits/reaps the owned helper, with a one-second
`WaitDelay` for cleanup. This is bounded helper ownership, not process-tree control
or a hard real-time guarantee. Diagnostics omit notification content, identifiers,
paths, and raw SDK/store/helper errors that could contain those values.

The native interface and callback fields were checked against the pinned Wails
`v3.0.0-beta.22` Go module source (`pkg/services/notifications/notifications.go`,
`notifications_darwin.go`, and `notifications_darwin.m`). Tests inject fake native
services and helper runners; process-ownership tests run only disposable children
of the test binary. They do not send notifications, execute AppleScript, access a
profile/vault/Keychain, or start the desktop application. Pure host cross-compiles
and build-tag policy tests are not native SDK execution evidence. Other desktop
startup, restart, opener, frontend, and dependency behavior is unchanged.

Parent full-source review and independent bounded security review approved
`ca5521f` with no findings. Go 1.26.10 cmd/host normal/race/vet, server/mcp/combined
host and targeted notification tests, and pure-host Windows/Linux compilation
passed (`v05-notification-parent-gate`, exit 0). Workflow YAML/actionlint passed
(`v05-notification-workflow-lint`, exit 0). The dedicated macOS CI lane builds
actual embedded assets from frozen dependency installs, then runs these synthetic
contracts; native delivery/buttons and physical activation remain unrun.
