# Native confirmation build boundary (first slice)

The desktop entrypoint now selects its existing human-confirmation policy through
`host.DesktopHumanConfirmationPolicy`. Only `darwin && !server && !mcp` is eligible
for the legacy embedded-native decision. Any nonempty `FRONTEND_DEVSERVER_URL`
still denies it. Windows, Linux, and unknown platforms remain denied. The pure
`HumanConfirmationPolicy(platform, transport)` is unchanged.

Wails v3 beta.22's default Darwin assets path is WKURLSchemeHandler
(`wails://localhost`) to an in-process HTTP request, then Assets middleware and
`/api`. The SDK `server` build instead exposes Assets through TCP; the SDK `mcp`
build adds an optional-token TCP JavaScript-evaluation surface. These build modes
must not inherit native human capability from `runtime.GOOS` alone. Host, Origin,
ports, and window headers are not evidence of trust. No custom Wails
`Options.Transport` is configured; adding one requires explicitly denying this
selection until independently verified. A source-wiring test locks that assumption.

## Deliberately unchanged

`TrustedHumanConfirmations` gates bundled MCP creation/write tools, not central
approval authorization. This guard does **not** authenticate all `/api` requests,
secure SDK MCP `js_eval`, attest a WebView, or prove a physical human gesture.
Headless defaults and approval endpoints are unchanged. Central request
authorization and native attestation need a separate design.

Build-tag unit/race tests cover default, `server`, `mcp`, and combined modes.
Cross-platform host test binaries can be compiled without desktop initialization.
Source and pure tests are not native runtime proof. An isolated, fake-backed
Darwin runtime experiment and its exact evidence/limits belong under ignored
`.cache/native-boundary-proof/`, not in the production application.
