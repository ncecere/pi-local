# v0.3 plan: trust and control

Goal (roadmap.md): you can leave agents running unattended. Six workstreams, each full-stack (Go, runtime, UI, tests,
`docs/api.md`), built in two waves of three, each in its own worktree and branch, merged after v0.2.0 is tagged.

Shared rules: Go tests in `internal/app` (the fake provider scripts `CALL:<tool>:<json>`, `READ:`, `RUN:` …), runtime
tests with vitest, frontend tests with vitest; `make check` green; secrets only through `secrets.Store`
(`secrets.NewMemory()` in tests); app.db has one connection (never query inside an open rows loop); copy is plain,
short, sentence case.

## Wave 1

### A. Approvals 2.0: rules, profiles, "always allow", fast-judgment tightening

Today `agent.yaml` `approvals: {tools: [names or globs], timeoutSeconds}`: listed tools ask first.

- **Rules.** `approvals.rules: [{tool, args?: {<arg>: <glob>}, action: allow | ask | deny}]`, first match wins, before
  `tools`. `args` globs match the argument's string value (`*` any characters; `command: "git status*"`). `deny`
  refuses without asking (the model is told "Not allowed by your approval rules").
- **Profiles.** `approvals.profile: careful | balanced | trusting | custom` (new agents: balanced; existing agents
  keep their `tools` as custom).
  - careful: every tool that can change something asks (write, edit, bash, schedule, notify_person excluded, MCP tools
    not marked read-only by their annotations).
  - balanced: bash, and MCP tools marked destructive (or not marked read-only and named like delete/send/remove/
    update/create/write/post), ask.
  - trusting: nothing asks, except the built-in deny/ask rules below.
  - Built-in rules for every profile (shown, can't be removed, ask): `bash` commands matching `rm -rf*`, `sudo *`,
    `git push --force*`, `* | sh`, `curl * | *sh`.
- **"Always allow".** The approval card gets "Approve and always allow this" (exact tool + the arguments it chose:
  for bash the command's first word and subcommand, e.g. `git status*`; for others the tool alone). It adds a rule
  via `POST /api/agents/{id}/approval-rules`. Rules are listed and removed on the agent's Tools tab.
- **Fast-judgment tightening** (use `approvals`, off unless fast judgments are on): a tool call the rules would let
  run is judged ("could this cause harm or be hard to undo?", noul ≥ threshold) and then asks, with
  "Asked because fast judgments thought it could be risky." Never loosens. Fails open to the rules.
- Where: the runtime's approval hook (`runtime/src/lib/approvals.ts`) evaluates; the app validates config
  (`internal/agents/config.go`), renders the policy to `TOOL_APPROVALS`, and the gateway answers `/judge/approval`.

### C. Budgets, prices, usage drill-down

- **Known prices.** `internal/models/prices.go`: a table of list prices (per million input / output / cache tokens) for
  well-known models (OpenAI, Anthropic, Google, Mistral, DeepSeek; matched by model ID, with dated suffixes). A model
  added without prices gets them (marked `priceSource: "list"`); the person can change them (`"you"`).
- **Budgets.** `agent.yaml` `budget: {monthlyUsd, onExceed: stop | warn}` and an app-wide monthly budget in Settings →
  Usage. At 80% a `budget` event (and a notification); at 100% with stop, messages, schedule runs and asks to that
  agent are refused (`402 over_budget`, "Hardac reached its $20 budget for October. Raise it in its settings.");
  with warn, a banner only. Usage the budget counts: this calendar month, priced models only (unpriced counted
  separately and said).
- **Drill-down.** `GET /api/me/usage` gains `?agent=`, `?model=`, grouping by day/agent/model; the Usage page gets
  filters and per-agent and per-model tables with cost and requests, and a month view.

### F. Backups, backup before update, diagnostics

- **Backups.** `POST /api/backups` writes `<data>/backups/pi-local-<date-time>.zip` (or a chosen folder): app.db via
  `VACUUM INTO`, every agent folder (`agent.yaml`, `memory.json`, `state.sqlite` copied with SQLite's backup API
  through the runtime when awake, or the file when asleep), templates. Never secrets (the keychain isn't copied; the
  backup lists which keys will need entering again). Daily automatic backup (on by default, keep 7), Settings →
  Backups lists, reveals, deletes, and restores (restore: quits agents, moves the current data aside to
  `<data>/before-restore-<date>`, unpacks, restarts).
- **Before update.** `internal/update` makes a backup before installing.
- **Diagnostics.** `POST /api/diagnostics` (desktop: save dialog) writes a zip: versions, OS, settings without
  secrets, agent configs without secrets, the last 2,000 lines of each log (redacted with the same rules as
  approvals), recent errors. Settings → About "Save diagnostics…".

## Wave 2

### B. Audit log and "what the agent did"

- The runtime reports each tool call when it ends (name, redacted arguments, outcome ok/error/denied, duration,
  approval decision) to the gateway `/activity`, batched; the app also records messages sent, schedule runs, asks,
  approvals decided, sign-ins, and errors. Table `activity` in app.db; kept 90 days.
- `GET /api/activity?agent=&thread=&kind=&before=&limit=`; `GET /api/activity/export` (CSV).
- UI: Settings → Activity (filters, export); the agent's Activity tab; a conversation's "What happened" timeline
  (steps with times and durations, from the view's tool calls plus activity).

### D. Secret scrubbing

- The runtime scrubs tool output before the model sees it and before it is stored: values that look like
  credentials (the patterns in `redact.ts`, applied to tokens in text) and the runtime's own secret values (its model
  key, its MCP servers' env and header values) become `[redacted secret]`. MCP results, bash output, read output,
  web fetch, ask replies.
- The UI never shows a secret the transcript didn't (already true when the runtime scrubs). Logs are redacted too.
- A per-agent switch (on by default) for agents that must handle tokens.

### E. Sandboxed shell (macOS first)

- `bash` runs under `sandbox-exec` with a generated profile: read anywhere except `~/Library/Keychains`, `~/.ssh`,
  `~/.gnupg`, the app's data folder outside this agent; write only the workspace, the agent's temp folder and
  `/dev/null`; network on or off per agent (default on). Platform interface so Linux (bubblewrap) and Windows
  (AppContainer) slot in at v0.5.
- `agent.yaml` `workspace.sandbox: on | off` (new agents on). With the sandbox on, the balanced profile stops asking
  for bash (the built-in rules still ask).
- A denied write reads plainly to the model ("The sandbox blocked writing outside the workspace").
